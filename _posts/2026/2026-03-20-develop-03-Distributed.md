## MQ消息
### MQ消息堆积
1. **消费能力不足**
  - 消费者处理慢 / 线程数少
  - 单线程消费 → CPU / IO 瓶颈
2. **消息流量突发**
  - 突然业务高峰，消费者瞬间跟不上
3. **消费者宕机或异常**
  - 消费者挂掉 → 消息不断堆积
4. **消息积压在从库**
  - MQ 集群主从同步慢（如 RocketMQ Master → Slave）
  - 消息未同步完成，从库 lag

1️⃣ 增强消费者能力
✅ 并行 / 批量消费
- Kafka / RocketMQ 支持批量消费
- 批量提交 offset / ack
- CPU/IO 并行处理，提高吞吐量
  ✅ 弹性扩容消费者
- 通过消费组水平扩容
- 消费者数量动态调整
  2️⃣ 消息过期与限流
  ✅ 消息 TTL（Time To Live）
- 过期消息自动删除
- 防止长期堆积导致存储爆炸
  ✅ 流量削峰
- 生产端限流（慢生产）
- MQ 端限速
- 下游系统限流
  3️⃣ 优先处理堆积队列
  ✅ 堆积队列检测
- MQ 监控：
  - lag / 未消费数量
  - 队列堆积报警
    ✅ 消费策略调整
- 临时增加消费者实例
- 调整消费顺序（优先堆积消息）
  4️⃣ 从库堆积特定处理（主从同步堆积）
- RocketMQ / Kafka 从库堆积，可能是：
  - 网络延迟
  - 从库消费慢
  - Master 压力大
    处理方式：
1. **提升从库同步能力**
  - 增加网络带宽 / IO
  - 调整批量同步参数（batch size / flush interval）
2. **从库落后告警**
  - 监控 lag / backlog
  - 超过阈值触发扩容或处理
3. **临时读主库**
  - 堆积严重时，从库读改为直接读主库
  - 避免从库数据延迟影响业务
    5️⃣ 数据持久化和重试机制
- **消息重试策略**
  - 消费失败 → 延迟重试 / DLQ（死信队列）
- **持久化存储**
  - 消息落盘，保证不会丢失
- **重复消费幂等**
  - 消费者处理幂等设计，避免重复处理

### 顺序消费
如何在堆积严重、并行处理、从库同步慢的情况下，保证顺序一致

1️⃣ 分区 / 队列绑定
- **Kafka / RocketMQ / Pulsar** 等支持 **消息分区（Partition）**
- 核心思想：
  - 同一业务（如同一订单ID） → 发送到同一个分区 / 队列
  - 队列内部保证 FIFO → 消费顺序一致
    2️⃣ 单线程 / 单消费者队列处理
- 对于必须严格顺序的业务，使用 **单线程消费队列**
- 消费者按顺序处理消息
- 堆积严重时：
  - 可以通过 **分片队列**（多个订单ID分到不同队列）平衡吞吐
    3️⃣ 顺序消费 + 并行消费（分组策略）
- 将业务按 **逻辑 key 分组**
- 同一分组顺序处理，不同分组并行处理
- RocketMQ 支持 **MessageQueueSelector** → 指定队列
- Kafka 通过 **同一 key → 同一 partition**
  4️⃣ 消费幂等 + 顺序控制
- **消费端设计幂等**：
  - 即使顺序偶尔打乱，也能保证最终一致性
  - 使用版本号、时间戳、状态检查
- **顺序控制机制**：
  - 本地缓存排序 → 按 sequenceId 依次处理
  - 或使用 **事务消息** / **延迟队列**保证顺序执行
    5️⃣ 从库同步 + 顺序问题
- 如果是从库堆积，顺序消费可能被打乱
- 企业做法：
  1. 消费端从主库读取最新消息（确保顺序）
  2. 严格分区 + 单线程队列处理
  3. 或使用 **全局 sequenceId + 幂等消费** 保证一致性


### 多发（重复）、漏发（丢消息）、重复消费（幂等）

1、重复发送：
- 网络重试（最常见）
- 生产者不知道发送是否成功
- MQ没有严格去重机制
  解决方案：
- 业务唯一ID（核心）
- 生产者端“发送确认”
- 本地消息表

2、 消息丢失：
- 生产者 → MQ
  - 开启确认机制（ack/confirm）
  - 失败重试
- MQ本身丢消息
  - 持久化
- MQ → 消费者
  - 手动ack

3、重复消费
- 幂等性设计
  - 数据库去重
  - 状态机控制
  - Redis去重
