   微服务架构是将单体系统按业务边界**拆分**为多个独立服务，每个服务独立部署、**独立**扩展，通过轻量通信协作，从而提升系统的可维护性和**扩展**性。

## 系统设计
- 服务拆分
  - 拆分原则
    - **按业务领域拆分（DDD思想）**
    - 高内聚、低耦合
    - **单一职责**
      粒度 = 一个服务承载的业务边界大小
- 是否围绕“业务能力”拆分（最重要）=一个完整业务能力
- 是否符合“高内聚、低耦合”
- 是否能“独立演进”：单独升级、部署、扩展？
- 团队规模匹配：“服务很多，但没人维护得过来”

拆得过细会怎样？
- 延迟高
- 调试困难
- 链路追踪复杂
- 分布式事务泛滥
- 运维成本暴涨
- 性能下降：网络调用比本地调用慢很多
- 开发效率反而下降

拆得过粗会怎样？
- 变成“伪微服务”（其实是单体）
- 无法独立扩展
- 代码耦合严重
- 部署风险大

第一步：按业务模块拆（粗粒度）
第二步：瓶颈出现再拆
第三步：热点拆分
- 查询多  单独读服务
- 写多  单独写服务

### SSO（单点登录）方案
主流 SSO 方案（核心就这 4 类）
1️⃣ **Cookie + 同域方案**（最简单）
适用：
- 内部系统（统一域名）
  2️⃣ **Token（JWT）方案**（现在最常用）
```
用户 → A 登录成功 → 返回 JWT
        ↓
访问 B → 携带 JWT
        ↓
B 校验 JWT（公钥/密钥）
```
关键点：
- Token 存储：
  - localStorage
  - Cookie
- 校验方式：
  - JWT 自校验（无状态）
  - 或调用认证中心
    优点：
- 无状态（适合微服务）
- 跨域支持
- 扩展性强
  缺点：
- Token 泄露风险
- 需要统一认证规范
  3️⃣ **SSO 中心**（CAS / OAuth2 / 统一认证中心）
  代表协议：
- CAS（老牌）
- OAuth2
- OpenID Connect（OAuth2升级版）
```
用户访问 B（未登录）
        ↓
跳转到 SSO 登录中心
        ↓
登录成功 → 返回 Ticket / Token
        ↓
B 校验 → 登录成功
```
核心组件：
- 认证中心（Auth Server）
- 各业务系统（Client）
  优点：
- 标准化
- 支持跨域、跨系统
- 安全性高
  缺点：
- 架构复杂
- 需要统一建设
  4️⃣ 网关统一认证（企业常用）
  流程：
- 用户登录 → 获取 Token
- 所有请求都走网关
- 网关负责：
  - 鉴权
  - Token 校验
- 后端服务不关心登录
  优点：
- 统一认证入口
- 后端服务无感知
- 易于扩展
  缺点：
- 网关压力大
- 强依赖网关稳定性

#### 难点
1️⃣ 退出登录（单点登出）
- A 退出 → B 也要退出
1. 前端驱动登出（最简单，但不靠谱）
2. 后端通知登出（标准 SSO）：SSO 中心通知（标准方案）
3. **Token 失效机制（JWT 场景）**

2️⃣ Token 失效
- 怎么让所有系统同步失效？
  JWT 默认是无法“主动失效”的
  ✅ 方案 1：黑名单（常用）
  退出时：把 Token 加入 Redis 黑名单
  ✅ 方案 2：短 Token + 刷新机制（推荐）
  设计：
- Access Token：5~15 分钟
- Refresh Token：长时间
  ✅ 方案 3：版本号机制（高级）
  用户表里加：token_version = 1
  JWT 带上：version = 1
  退出时：token_version++
  校验时：JWT.version != DB.version → 失效

3️⃣ 权限同步
- A 和 B 权限模型不一致怎么办？
  用户身份可以统一（SSO），但“权限语义”不统一
  1️⃣ 权限下沉（各系统自己管）【最常见】
  思路：
- SSO 只负责：
  - “你是谁”（身份认证）
- A / B 各自负责：
  - “你能干什么”（权限控制）
    2️⃣ 统一权限中心（RBAC 中台）
    3️⃣ 权限映射（推荐你重点说）
    **统一“抽象权限”，各系统做“映射”**
    ❗ 权限变更如何同步？
- 推模式（推荐）：权限中心 → MQ 通知 A/B
- 拉模式：定时刷新
- 强制重新登录：Token 失效

### 日志链路跟踪
日志链路跟踪的核心概念：如何把一次请求的所有操作串起来，形成完整链路，方便排查？
1. Trace（全局请求）
  - 一个用户请求，跨服务的唯一标识
  - 全局唯一 ID
2. Span（一次调用）
  - Trace 的一个节点，表示服务或方法调用
  - 每个 span 有：
    - spanId（唯一）
    - parentId（上游 span）
    - timestamp / duration
3. Context Propagation（上下文传递）
  - TraceId/SpanId 从服务 A 传到 B、C
  - HTTP header / RPC metadata

1️⃣ 基于日志埋点（最基础） 需要人工 grep
2️⃣ 链路追踪框架（企业主流）：SkyWalking
3️⃣ 日志 + TraceId 结合
- 日志系统（ELK / ElasticSearch）
- 每条日志都带上 TraceId
- TraceId → 关联不同服务的日志
- 优点：
  - 即使不做可视化，也能排查问题
- 缺点：
  - 人工分析慢
  - 不方便统计性能指标

### 对外部系统开放的 API 接口
安全设计：
防止你提到的数据泄漏和越权访问

认证与授权（防非法进入）
- 接入校验：不能只靠账号密码。通常采用 `AppID + AppSecret` 模式。
- 签名机制（API Signing）：为了防止请求内容被中途篡改，必须使用签名。
  - _做法_：发送方将请求参数 + 时间戳 + 随机数，通过 **HMAC-SM3**（或 SHA256）算法生成签名字符串。接收方（A系统）用同样的逻辑重算一遍。
- 防止重放攻击：要求接口带上 `nonce`（随机字符串）和 `timestamp`。A 系统会记录最近 5 分钟内的 `nonce`，如果重复则直接拒绝。

防范越权访问（核心痛点）
越权分为“水平越权”（看别人的数据）和“垂直越权”（做不该做的操作）
- 对象级隔离：在 SQL 层面上，所有查询必须强制绑定 `partner_id` 或 `user_id`。绝不相信调用方传过来的 `order_id`，而是查询 `WHERE id = ? AND owner_id = ?`。
- 令牌绑定：如果使用 Token，Token 内部应包含该调用方的权限范围（Scopes），在 API 网关层（如 Spring Cloud Gateway + Sentinel）直接拦截超出权限的请求。

数据防泄漏
- 传输加密：强制使用 **HTTPS (TLS 1.2/1.3)**。如果是金融级，可能需要双向证书认证（mTLS）。
- 响应脱敏：接口返回的数据要精简。比如返回用户信息时，手机号必须是 `138****0000`，只在必要时提供专门的解密接口。
---
容错与稳定性设计
限流与熔断（自保）：
- **针对 IP/AppID 限流**：防止某一个对接方并发过高。
- **针对全局限流**：保护 A 系统的数据库不宕机。
  幂等性设计（容错核心）：
- 要求对接方请求时带上唯一的 `request_no`。A 系统利用 Redis 或数据库唯一索引做幂等校验，如果发现该编号已处理过，直接返回之前处理成功的结果。
  异步处理与补偿：
- 针对关键金融接口，每天晚上进行数据对账，发现状态不一致的自动发起补偿流程。

---
发生泄漏/越权了怎么办？
- **熔断切断**：第一时间在网关层关闭该受损 `AppID` 的访问权限。
- **密钥轮换（Key Rotation）**：立即废弃当前的 `AppSecret`，要求对方重新生成并下发。
- **日志溯源**：
  - **审计日志**：A 系统必须记录所有接口的入参、出参、IP、处理时长和操作人。
  - 通过 Elasticsearch 查询该 AppID 近期的异常访问模式（比如短时间内遍历了大量不属于它的 `order_id`）。
- **数据加盐/重哈希**：如果是密码类泄露，强制所有用户重新登录并更新加密状态。


###  用户隔离、资源分配、扩展是怎么设计

用户隔离设计 (Isolation)
隔离是系统的安全底线，防止 A 的数据被 B 看到。
SaaS 模式：**多租户隔离** (Multi-Tenancy)
在 SaaS 中，隔离的对象是**租户（Tenant）**。
- 字段隔离（共享 Schema）：最常用。所有表增加 `tenant_id`。
  - _实现细节_：在持久层（如 MyBatis-Plus 或 Hibernate）使用 数据权限拦截器，自动在 `WHERE` 条件中注入 `tenant_id`，防止开发人员漏写。
- 逻辑隔离（独立 Schema）：每个租户一个 Schema。
  - _实现细节_：使用动态数据源（Dynamic DataSource）。通过 ThreadLocal 存储当前请求的 `tenant_id`，在 `RoutingDataSource` 中动态切换连接池。
- 物理隔离（独立数据库/实例）：针对金牌客户或高安全要求客户。直接分配独立的 DB 实例。
  B2B2C 模式：角色与维度隔离
  在 B2B2C 中，隔离是对业务主体（平台、商家、用户）的权限划分。
- 数据可见性：商家只能看到所属店铺的订单；用户只能看到自己的订单；平台看全量。
- 实现方式：基于 RBAC（Role-Based Access Control）模型。隔离通常体现在 业务关联表 上，而不是底层的租户 ID 注入。


资源分配设计 (Resource Allocation)
如何确保大流量客户不把小流量客户的资源“挤死”？
SaaS：**资源配额与流控**
- 配额管理 (Quotas)：根据订阅版本（标准版 vs 企业版）限制资源。例如：存储空间 5GB、API 调用次数 1万次/天。
- 多租户限流：使用 Redis + Lua 脚本或 Sentinel。限流 Key 不仅仅是 API 路径，而是 `api_path + tenant_id`。
- 线程池隔离：关键租户可以分配独立的线程池，避免由于某个租户的复杂查询导致整个微服务线程耗尽。
  B2B2C：业务优先级与分片
- 活动隔离：B2B2C 经常面临“大促”或“秒杀”。通常采用**业务隔离**，比如将头部商家的流量引导至专属的 Hystrix 熔断策略或独立的集群。
- 存储倾斜处理：如果某个超级大卖家数据量极大，需要通过分库分表（Sharding-JDBC）将该商家的订单路由到特定的表分区中，避免单表瓶颈。

扩展性设计 (Scalability)
SaaS：**横向扩展**与热迁移
- 水平扩容：SaaS 倾向于“无状态化”。只要增加 Pod 实例，通过负载均衡即可承载更多租户。
- 热迁移能力：当某个数据库下的租户过多时，需要具备将某个 `tenant_id` 的所有数据一键迁移到新数据库的能力（通常结合 CDC 技术如 Canal）。
- 配置化扩展：SaaS 的功能扩展依赖于插件化（SPI）或动态脚本。比如 A 租户需要一种计费逻辑，B 租户需要另一种，代码通过策略模式动态加载。
  B2B2C：纵向业务解耦
- 领域驱动设计 (DDD)：B2B2C 扩展性体现在业务模块的解耦。例如将“支付结算”从“订单系统”中独立出来，方便对接不同的支付渠道。
- 开放平台 (Open API)：为了扩展生态，B2B2C 往往需要构建类似淘宝的 Open Platform，允许第三方开发者通过 OAuth2 接入商家的店铺数据，实现 ERP 自动同步。
  对比总结表

| 特性   | SaaS 设计重点                | B2B2C 设计重点       |
| ---- | ------------------------ | ---------------- |
| 隔离核心 | `tenant_id` 自动拦截与数据源动态切换 | RBAC 权限模型与业务关联字段 |
| 资源分配 | 按订阅等级限流、存储配额、计算隔离        | 针对高并发场景（秒杀）的流量削峰 |
| 扩展路径 | 追求“一套代码支撑万人”的通用配置化       | 追求“业务模块化”的快速垂直扩展 |

## 安全体系
微服务安全 = 认证（你是谁） + 授权（你能干啥） + 防护（你有没有恶意） + 审计（你干了啥）

认证（Authentication）——你是谁？
1️⃣ 主流方案：JWT + OAuth2
你可以这么说：
> 我一般采用 **Spring Security + OAuth2 + JWT** 做统一认证中心
- 用户登录 → 认证中心（Auth Service）
- 返回 **JWT Token**
- 后续请求：
  - Header 带 `Authorization: Bearer token`
  - 网关统一校验
    2️⃣ 为什么用 JWT？
- 无状态（适合微服务）
- 不依赖 session（支持横向扩展）
- 减少认证中心压力
  3️⃣ Token设计（这里是加分点）
- 过期时间（access_token 短期 + refresh_token）
- 签名算法（HS256 / RS256）
- 防篡改
- 可以加入：
  - 用户ID
  - 角色
  - 权限范围

授权（Authorization）——你能干什么？
1️⃣ RBAC 模型（必讲）
> 用户 → 角色 → 权限
- admin → 所有权限
- user → 查询权限
  2️⃣ 在哪做权限控制？
  ✅ 网关层（粗粒度）
- 是否登录
- 是否有接口访问权限
  ✅ 服务层（细粒度）
- 方法级权限控制（如：
  - `@PreAuthorize`  
    ）

访问入口安全（核心：网关）
> 所有请求必须先经过 API 网关（比如 Spring Cloud Gateway）

✅1. Token校验
- 是否有效
- 是否过期
  ✅ 2. 黑名单机制
- Token 被踢下线
  ✅ 3. 限流（防刷）
- IP限流
- 用户限流
  Redis + 令牌桶 / 漏桶算法

防止恶意访问（重点）
1️⃣ 限流（Rate Limit）
- 爬虫
- 暴力刷接口
  方案：
- 网关限流（Redis）
- Sentinel / 自定义限流
  2️⃣ 防重复提交（幂等）
  防止：
- 用户重复点击
- 攻击请求重放
  方案：
- Token + Redis 去重
- 唯一请求ID（requestId）
  3️⃣ 防止重放攻击
  核心思路：
- 请求带：
  - timestamp
  - nonce（随机数）
  - 签名
    服务端：
- 校验时间窗口（比如5分钟）
- nonce 不可重复（Redis）
  4️⃣ 防 SQL 注入 / XSS
- ORM框架（MyBatis 预编译）
- 参数校验
- 输出转义
  5️⃣ 防暴力破解
  登录接口：
- 错误次数限制
- 验证码（图形 / 滑块）
  6️⃣ IP黑名单 / 风控
- 异常IP封禁
- 地域限制
- 行为分析（风控系统）

服务间调用安全
微服务之间也要安全：
1️⃣ 内部认证
- 服务间调用也带 Token
- 或使用 mTLS（双向证书）
  2️⃣ 防止伪造服务调用
- 网关外部入口唯一
- 内部服务禁止直接暴露

数据安全
1️⃣ 传输加密
- HTTPS（TLS）
  2️⃣ 存储加密
- 密码：BCrypt
- 敏感字段：AES

审计 & 日志（很多人不说，但很加分）
- 登录日志
- 操作日志
- 安全审计

> - 防护：防刷、防重放、防SQL注入

> - 审计：日志追踪

## 系统拆分重构

在不影响业务的前提下，逐步把“混乱系统”演进成“可维护系统”。
系统拆分重构通常是从单体或耦合严重的系统出发，按照业务边界**逐步拆分**为多个服务，同时通过**灰度**发布、数据迁移和兼容设计，保证业务平滑过渡。
- 常见问题：
  - 模块耦合严重（改一个地方全挂）
  - 发布风险高
  - 性能瓶颈明显
  - 团队协作困难
- 领域建模 & 服务划分（核心）
  - 按业务域拆（DDD思想）
- 拆分策略
  - 按业务模块逐步迁移
  - 读写分离拆分
  - 接口优先拆分
- 数据拆分
  - 一个服务一个库
  - 数据迁移策略：双写，校验一致性，最终切流
  - 避免跨库事务：MQ
- 接口兼容 & 灰度发布
- 分布式问题处理
  - 分布式事务
  - 幂等问题
  - 服务调用失败：Sentinel
- 观测与回滚机制 ：Prometheus/Grafana
  - 日志
  - 报警
  - 回滚方案：流量切回旧系统，数据兜底

## 高并发
高并发 = 同一时间有大量请求同时访问系统
- 系统扛不住（CPU / 内存 / IO）
- 响应变慢（延迟高）
- 直接挂掉（宕机）

- CPU高 → 代码问题
- DB慢 → 索引 or 分库+缓存
- QPS突增 → 限流 + MQ

单点：
1️⃣ 提升代码执行效率
- 减少锁（避免 synchronized）
- 使用线程池
- 异步处理（CompletableFuture）
  2️⃣ **缓存**（核心手段）
- 避开数据库 80%请求直接命中缓存，DB 压力下降
  3️⃣ **限流**（防止系统被打死） ： Sentinel/Nginx 限流
- 令牌桶
- 漏桶
  4️⃣ 降级 & 熔断
- 推荐服务挂了 → 返回默认数据
- 防止“雪崩”
  5️⃣ 异步削峰（**MQ**）
- 秒杀下单
- 日志处理

从单点到集群
1️⃣ **应用层集群**（无状态化）
- Session 不放本地
- 放 Redis / Token（JWT）
  2️⃣ **负载均衡**
- Nginx
- LVS
  - 轮询
  - 权重
  - IP hash
    3️⃣ **数据库扩展**
- 读写分离
- 分库分表（核心难点）

分布式架构：
网关 → 微服务集群 → 缓存 → MQ → 分布式数据库
1️⃣ 网关（统一入口）
- 鉴权
- 限流
- 路由
  2️⃣ 微服务拆分
- 订单服务
- 用户服务
- 支付服务
  3️⃣ 分布式缓存（Redis集群）
- 热点数据
- 高QPS
  4️⃣ 消息队列（MQ）
- 削峰填谷
- 解耦
  5️⃣ 分布式锁
- 并发写冲突
