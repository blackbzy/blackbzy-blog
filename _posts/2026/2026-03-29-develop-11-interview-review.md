不进入二级内存：**不进入用户态 buffer（Java heap / 应用内存）**，操作系统文件一定会进入**内核页缓存（Page Cache）**
mmap =内存映射文件（memory map）：把文件“映射”到进程虚拟内存里，让你像操作内存一样操作文件=》用户态和内核态“共享同一块物理内存”
- 不是传统 IPC 共享内存，用户空间和内核空间共享页缓存
-  多个进程映射同一个文件，实际指向同一块物理内存
- 进程看到的是“虚拟地址”，而不是物理内存
  ❌ mmap 缺点
1. **大文件可能触发缺页异常（page fault）**
2. **内存不可控（容易 OOM）**
3. **并发写复杂（需要同步）**
4. **在 Java 里不好释放（经典坑）**
   所以：
   1️⃣ **大文件随机读取 / 小范围访问**：无需一次性读整个文件
   2️⃣ **只读大文件，访问模式可预测**：读取配置文件、只读日志分析
   3️⃣ **进程间共享内存**
   4️⃣ **零拷贝输出**

- **Java + FTP 网关 → 基本用不了 sendfile（至少不是你想象的那种）**
- **需要“解析文件” → 一定会回到用户态 → sendfile 失效**
- **本地 IO 并不一定慢，很多时候是你对 IO 的理解有偏差**

为什么 FTP + Java 很难用 sendfile？
👉 必须满足：
- 数据已经在**本地文件系统**
- 有**文件描述符（fd）**
- 目标是**socket**

追求性能（不用解析）：FTP →（下载）→ 本地文件 → sendfile → 客户端
需要解析（你现在的情况）：FTP → InputStream → Java解析 → 输出
linux下 写文件：write() → Page Cache（内存） 并不会立刻写磁盘！
Java → 内核 Page Cache →（异步）→ 磁盘
真正慢的是：
- 网络 IO ❗
- 随机磁盘 IO ❗
  不是：
- 顺序写 + Page Cache
  Page Cache 是 **Linux 内核为文件 I/O 提供的内存缓存**：特点：顺序读写大块数据时，内核直接在内存操作，速度非常快。磁盘写入是异步的。
  大 buffer 读取
- Java `BufferedInputStream` 或 NIO `ByteBuffer`
- 例如 16KB/32KB 一次读取，减少系统调用（read）
  顺序写 + 大 buffer
- 每次写几十字节会触发系统调用
- 每次写几 KB 或更大，充分利用 Page Cache
- **异步刷盘**
  - Linux 默认后台 flush
  - 你的 Java 写操作几乎等于内存操作，不阻塞
    顺序写的本质：应用程序按文件偏移线性写入数据，连续写入，不跳跃、不随机修改文件
- `FileOutputStream` 默认从文件开头或末尾写（append=false 就从头开始写，append=true 从尾部）
- 你一次 write 一个字节数组，**按顺序填满文件**
- 内核会把这些连续写入映射到 Page Cache 的连续页
  即使你没做特殊操作，天然就是顺序写，因为文件写入是线性、按偏移连续的。

流式解析（推荐）：FTP → InputStream → 边读边解析 → 边输出
- **一定会占用 CPU**（解析本质就是计算）
- **内存可以控制得很低**（只要不用一次性加载）
- 一般不需要“序列化”，除非你要跨进程/存储
  不要按大小切，要按协议切，不需要预先知道每一行的字节长度，而是通过分块读取数据并基于分隔符（如换行符）进行切分。**对于跨 buffer 的数据，可以通过维护一个残留缓冲区，将上一块未解析完整的数据与下一块数据拼接后再进行解析，从而保证数据完整性。** 只在“完整行”时才解析。
  文件格式就是一行一行，然后用|隔开，按接口每格不同长度，但是每列固定长度：配置化每列的长度
  流式读取  
  ↓  
  byte[]（一行）  
  ↓  
  按 offset + length 解析  
  ↓  
  直接转数值 / 字段
  数据可能错位：
- 校验 `line[offset] == '|'`
- 做数据校验

**B2B2C 是一种商业/业务模式**，描述的是商品或服务如何流向最终消费者=》业务流程；
而 **SaaS 是一种软件交付/部署模式**，描述的是软件如何被使用和付费，多租户。=》写**底层平台**，多租户数据源动态切换和自定义表单引擎。


| **维度**   | **B2B2C 架构 (Business to Business to Consumer)** | **SaaS 架构 (Software as a Service)**  |
| -------- | ----------------------------------------------- | ------------------------------------ |
| **关注点**  | **价值链的传导**。如何连接平台、商家和消费者。                       | **资源的共享与隔离**。如何让一套代码服务于成千上万个客户。      |
| **数据结构** | **三级主体模型**：平台数据、入驻商家数据、终端用户数据。                  | **租户隔离模型**：通过 Tenant ID 区分不同企业客户的数据。 |
| **核心挑战** | 结算清分、多级库存管理、跨店铺的营销引擎。                           | 高并发下的多租户隔离、动态配置、灰度发布。                |
|          |                                                 |                                      |
核心算法：国密算法（SM系列）是硬要求：

|**算法类型**|**常用国密算法**|**对应国际算法**|**实际应用场景**|
|---|---|---|---|
|**对称加密**|**SM4**|AES|**数据存储加密**（数据库字段、文件加密）。速度快，安全性高。|
|**非对称加密**|**SM2**|RSA / ECC|**身份认证、数字签名、秘钥交换**。比如网银登录、合同签名。|
|**哈希算法**|**SM3**|SHA-256|**完整性校验、密码加盐脱敏**。防止数据被篡改，或存储用户密码摘要。|
每个算法在不同环节的作用
1. 存储环节 (Data at Rest)

- **对称加密 (SM4)：** 金融数据（如身份证号、银行卡号、余额）在进入数据库前，必须通过 SM4 进行字段级加密。
  - _作用_：即使数据库被“拖库”或运维人员违规查询，拿到的也是密文。
- **哈希算法 (SM3)：** * _作用_：存储登录密码时，绝对禁止明文，必须通过 SM3 进行“加盐（Salt）”哈希。此外，用于生成数据的“指纹”，防止数据在磁盘损坏或人为恶意修改时无法察觉。

1. 访问与传输环节 (Data in Transit
- **非对称加密 (SM2)：**
  - _作用_：建立安全通道（国密 SSL/TLS）。在客户端与服务器握手时，用 SM2 交换对称秘钥。同时用于**数字签名**，确保“你确实是你”，且发送的指令不可抵赖。
- **访问控制 (ABAC/RBAC)：** * 按照 JR/T 0197 标准，3级及以上数据（高敏感）在访问时必须进行**多因素认证 (MFA)**。

|**特性**|**聚簇索引 (主键索引)**|**非聚簇索引 (辅助索引)**|
|---|---|---|
|**叶子节点内容**|完整的行数据|索引字段值 + 主键 ID|
|**数量限制**|每个表只能有一个|每个表可以有多个|
|**查询速度**|极快（查到索引即查到数据）|较快（通常需要“回表”查询）|
|**物理存储**|物理上按索引顺序排列数据|逻辑上连续，物理上不连续|

1. LRU (Least Recently Used) - 最实用、默认首选：
  1. 淘汰**最长时间未被访问**的数据。认为“刚才用过的，待会大概率还会用”。
2. LFU (Least Frequently Used) - 针对长期热点：
  1. 淘汰**访问频率最低**的数据。认为“用得越多的越重要”。
3. W-TinyLFU (Window TinyLFU) - 现代“性能之王”：
  1. 它结合了 LRU 和 LFU 的优点。先让数据进入一个“窗口区”（LRU），如果表现好（访问频繁），再存入主缓存区（LFU 思想的过滤器）。
4. 基于 TTL + 随机抖动 (Random Jitter) - 业务层最稳
  1. **核心逻辑：** 给每个数据设置一个生命周期（Time To Live），但为了防止集体失效（雪崩），在设置时加上随机数。

面对一亿条数据这种量级，单机处理确实会遇到瓶颈。当我们要把单机架构扩展到 3 个节点（甚至更多）的分布式并行处理时，核心矛盾在于**“如何拆分任务”**以及**“如何保证不重不漏”**。
架构调整：从“单兵作战”到“集群协作”
- **引入任务调度中心：** 不能让三个节点盲目启动。需要一个“大脑”（如 XXL-JOB, Elastic-Job 或 Spring Batch Admin）来下发指令。
- **分片策略：** 调度中心告诉 A 节点：“你处理分片 0”，B 处理分片 1，C 处理分片 2。
- **去中心化 vs 集中式：** 如果不想引入复杂的调度器，可以使用消息队列（MQ）。把一亿条数据拆成若干小批次（比如每 1 万条一个消息）丢进 MQ，三个节点作为消费者竞争执行。这是最容易扩展的架构。

幂等性设计：一亿条数据的“保单”
- **数据库唯一索引（最底层保障）：** 建立业务流水号的 `UNIQUE KEY`。
- 状态机控制： 处理前检查该行数据的处理状态（`pending` -> `processing` -> `completed`）。
- **分布式锁 / 缓存去重：** 使用 Redis 的 `SETNX`。处理前先去 Redis 查一下这个 `DataID` 是否处理过。

|**方案**|**优点**|**缺点**|**结论**|
|---|---|---|---|
|**取模 (Row % 3)**|负载极其均衡，数据分布均匀。|**性能极差**。每个节点都要读取完整的一亿行数据，然后过滤掉不属于自己的。IO 开销是单机的 3 倍。|**不推荐**用于大文件。|
|**分段 (Range)**|节点只读取自己那一段。IO 效率高。|如果数据分布不均（比如前 3000 万全是坏数据），会导致负载不均衡。|**推荐**。适合处理静态的大文件或数据库大表。|

如何快速“定位”到第 3000 万行？
**方法 A：文件索引化（牺牲空间换时间）** 在处理前，先做一个“预处理”扫描。记录下每隔 100 万行的 **文件偏移量（Byte Offset）**。
- 节点 A 从 `0` 字节开始读。
- 节点 B 直接调用 `RandomAccessFile.seek(offset_3000w)` 快速跳转。
- 这样就避免了全量扫描。
  **方法 C：物理切割（最暴力也最有效）** 使用 Linux 指令（如 `split -l 33333333 bigfile.txt`）直接把一亿行的大文件物理拆分成 3 个小文件。每个节点只读自己的文件。虽然多了拆分步骤，但后续处理逻辑最简单，不需要考虑偏移量。
  分布式下的潜在问题：
- **数据倾斜：** 某个节点的分片全是复杂业务逻辑，跑得慢，另外两个节点空转。
- **分布式事务：** 如果一笔任务涉及多个数据库操作，一个节点挂了，如何回滚？（建议采用 TCC 或 Saga 模式）。
