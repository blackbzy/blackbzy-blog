### 最左匹配原因
数据在 B+ 树叶子节点里是这样排的：

```
(1, 1, 1)  
(1, 1, 2)  
(1, 2, 1)  
(1, 2, 3)  
(2, 1, 1)  
(2, 3, 1)  
(3, 1, 1)
```

排序规则是： 所以只能最左，且中间范围比较索引失效
1. 先按 a 排序
2. a 相同再按 b 排序
3. b 相同再按 c 排序

### innodb和MyISAM这两个的话,有什么区别?为什么
innodb
- 支持事务（ACID）

|---|---|---|
|事务|✅ 支持|❌ 不支持|

InnoDB：聚簇索引：
- **高效主键查询**
  - 主键查找直接定位叶子节点 → 一步到位
- **范围查询优化**
  - 数据连续存储，`WHERE id BETWEEN x AND y` 顺序扫描很快
- **事务与 MVCC 配合**
  - 数据行连续存储 → 行级锁操作快
  - Undo log、Redolog 都能顺序写，减少随机 I/O
- **减少 I/O**
  - B+树叶子节点存完整行
    MyISAM：非聚簇索引

### MVCC 是怎么实现的
保证事务隔离性 + 提高并发，不加全表/行锁
在每行记录中保存隐藏列
- **trx_id** = 创建/修改该行的事务 ID
- **roll_pointer** = 指向 Undo Log（旧版本数据）
- SELECT 查询不加锁（在默认的 REPEATABLE READ 隔离级别下）
  - MySQL 会读取 **符合当前事务可见性的版本**
- - INSERT / UPDATE / DELETE 会生成新版本
  - 并发事务通过隐藏列判断是否冲突
  - 行锁配合 MVCC 保证写安全
  - 读操作不会阻塞写 → 高并发

```md
#### 1. 字符串操作 (String)
- **`SET key value` / `GET key`**：最基础的读写。
- **`SETNX key value`**：Key 不存在时才设置（实现分布式锁的核心）。
- **`INCR / DECR key`**：原子计数器（常用于限流、点赞数）。 

#### 2. 哈希操作 (Hash
- **`HSET key field value` / `HGET key field`**：适合存储对象（如用户信息）。
- **`HMGET key field1 field2`**：批量获取对象的多个属性，减少网络 IO。

#### 3. 列表操作 (List)
- **`LPUSH / RPUSH key value`**：从左/右侧推入数据。 
- **`LPOP / RPOP key`**：从左/右侧弹出数据（可实现简单的消息队列）。
- **`BRPOP key timeout`**：阻塞式弹出，队列没数据时挂起等待。 

#### 4. 集合操作 (Set & Sorted Set)
- **`SADD key member` / `SISMEMBER key member`**：无序去重集合，判断元素是否存在（如点赞去重、共同好友）。
- **`ZADD key score member` / `ZRANGE key start stop`**：有序集合（常用于排行榜、延迟任务队列）。
  
```

### 缓存设计
- 缓存穿透 ：用户请求的数据在 **Redis 中没有**，在 **数据库中也没有**。
  - -**布隆过滤器 (Bloom Filter)：** 在缓存前加一层“网”，快速判断数据是否存在。不存在直接拦截。
  - **缓存空对象：** 如果 DB 查询结果为空，依然把这个 `null` 结果存入 Redis（过期时间设短一点，如 5 分钟），防止重复穿透。
- 缓存击穿 ：某个 **极热点 Key**（比如微博热搜、秒杀商品）在 **缓存过期的瞬间**，正好有海量并发请求进来。
  - - **热点 Key 不设置过期时间：** 由后台 Job 异步更新缓存，而不是依赖过期自动失效。
  - **互斥锁 (Mutex Lock)：** 发现缓存失效时，先拿 `setnx` 锁。拿到锁的线程去查 DB，没拿到的线程**等待并重试**从缓存读数据。
- 缓存雪崩 ：**大量 Key** 在同一时间 **集体过期**，或者 **Redis 挂了**。
  - - **设置随机过期时间：** 在基础过期时间上加一个随机扰动（如 $5-10$ 分钟的抖动），让 Key 均匀失效。
  - **双层缓存策略：** A 级缓存（短时长），B 级缓存（长时长/永久），作为兜底。
  - **限流降级：** 发现 DB 压力过大时，直接返回默认值或友好提示，保住核心服务。
### 用redis会有哪些问题？
1. 锁提前过期与“看门狗”问题
2. 释放了别人的锁（误删）
3. Redis 集群下的“异步丢失”
4. 任务状态的“罗生门”：它毕竟不是持久化数据库（即使开启 AOF 也有丢失风险）。
  1. Redis 只做“运行锁”和“瞬时缓存”，**关键的任务进度和状态必须持久化到数据库（MySQL）中**。
5. 大 Key 与持久化阻塞
  1. 读取或删除大 Key 会导致 Redis 线程阻塞（Redis 是单线程模型），这会拖慢所有依赖 Redis 的业务接口。

### Redis 不设置过期时间（TTL）会发生什么？
1. 内存耗尽（OOM）与内存淘汰
  1. 内存淘汰机制（Eviction）
    1. 如果你的淘汰策略配置的是 `volatile-lru`（只淘汰带过期时间的 Key），那么此时 **Redis 会直接报错 OOM**，拒绝所有写入操作。
    2. 如果配置的是 `allkeys-lru`（淘汰所有 Key 中最近最少使用的），Redis 会强制删掉一些“你以为永远不会丢”的数据来腾地方，导致业务出现难以预料的缓存穿透。
2. “脏数据”无法自动清理
3. RDB 物理快照与 AOF 日志膨胀

默认没有“统一标准”，**完全是你自己定**
- 常见：**10s / 30s / 60s**
- 原则：**必须 > 业务执行时间**
- 时间太短 → 锁提前释放（并发问题）
- 时间太长 → 死锁（资源浪费）
  还在用，就自动帮你续期；线程死了，就不续期让锁自动过期

### vastbase  E100 迁移工具 **exBase**

## oracle
### 1. 核心架构与存储
Sequence 的定义信息存储在系统表（如 `SYS.SEQ$`）中，主要包含
- **MINVALUE / MAXVALUE**：序列的范围。
- **INCREMENT BY**：步长（递增间隔）。
- **LAST_NUMBER**：**关键字段**。它记录的是当前已分配到内存 Cache 中的最大值，而不是当前被使用的值。

### 2. 内存缓存机制 (Cache Mechanism)
为了避免高并发下频繁读写物理表（造成 I/O 瓶颈和行锁争用），Oracle 默认会开启 `CACHE`。
- **工作流**：
  1. 当第一个请求调用 `NEXTVAL` 时，Oracle 会根据定义的 `CACHE` 大小（默认通常是 20），从系统表中一次性取出 20 个 ID 加载到 SGA（系统全局区）的一块专用内存中。
  2. 此时，系统表中的 `LAST_NUMBER` 会立即更新为当前的起始值 + 20。
  3. 随后的请求直接从内存中递增获取 ID，不需要访问磁盘。
  4. 当内存中的 20 个 ID 用完，Oracle 再次访问系统表，申请下一批号段。
- **注意点（跳号问题）**： 如果数据库突然宕机或实例重启，内存中尚未使用的 ID 就会丢失。下次启动后会从 `LAST_NUMBER` 开始重新申请，这就是为什么

### 3. 并发控制与 Latch

在高并发环境下，多个会话同时请求 `NEXTVAL` 时：
- Oracle 使用一种轻量级锁 **`row cache objects` latch** 来保护内存中的序列计数器。
- 由于只需要修改内存变量，这种锁的持有时间极短，性能远高于基于磁盘行的自增锁。

### 4. 关键参数的影响

在创建 Sequence 时，几个参数直接决定了其行为：
- **`ORDER` 与 `NOORDER` (默认)**：
  - `NOORDER`：在 RAC（多实例）环境下，每个实例拥有自己的 Cache，生成的 ID 只能保证唯一，不保证跨实例的绝对时间顺序。
  - `ORDER`：强制多个实例共享一个序列计数器，确保绝对递增顺序，但在高并发下会因为实例间通信产生性能损耗。
- **`CYCLE`**：当达到 `MAXVALUE` 后是否循环回 `MINVALUE`。
